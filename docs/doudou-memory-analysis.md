## TL;DR

- 逗逗的"场景记忆"本质是 **多模态感知 → 语义化记忆单元（场景）→ 跨场景检索/触发** 的闭环；官方未公开存储/检索细节，"跨游戏联想"大概率来自"存语义、不存应用"。
- oc-pet 现状是 **事件级文本记忆**：只存分类计数 + 最近一条话题 + 7 天摘要；且感知层产出的 `ActivityEvent`（含 summary/detail/时间轴）**没有进入记忆**——"感知→记忆"断链。
- "更底层"判断 **对一半**：对在感知层确实更基础、文本事件天然是场景记忆的原材料；错在"底层 ≠ 终局"，缺的是把信号沉淀为可回忆结构的 **三层加工：事件流采集 → 场景聚类 → 回忆触发**。
- 建议按 A→E 渐进落地，全部纯本地 / JSON 级 / 无新依赖；第一步是把 `today` 计数升级为带时间轴的事件流。
- 补充（v0.2）：纳入 deepseek-hanako 借鉴，升级全景图新增 **F（极简本地状态口 HTTP 只读，复用 `phone_receiver.py` 范式）** 与 **G（补全桌宠状态词表对齐 6 态 + 完成态庆祝）**；`hanako_monitor.py` 已有生命周期→情绪桥、`behavior_mixin.py` 已有 idle 微动作，故 hana-bridge 与 idle 小动作**不重复借鉴**。

## 1. 逗逗 1.0 场景记忆系统拆解

> 依据：官方文章 + 2025-08 多家媒体报道（详见文末来源表）。**标注【推测】的为官方未公开、基于公开信息的推断。**

| 维度 | 公开信息（已核实） | 内部机制（推断） |
|------|------------------|------------------|
| **存什么** | 视觉、听觉、对话等多模态信息融合为可记忆的"场景"；不只记对话片段；场景中理解"与你的关系"并形成自我认知；对竞技对局可做全局点评 | 【推测】场景 ≈ 多模态编码后的语义块 + 元数据（时间/游戏/情绪/关系标签），而非原始视频/音频长期存储 |
| **以什么为单位** | 以"场景"为单位长期储存共同经历；"对于每一个场景都有相应的回放"；记忆时间"无限延长" | 【推测】记忆容量靠"长上下文窗口 + 外部场景库 + 摘要压缩"分层管理 |
| **如何检索/触发回忆** | 环境感知到一定状态时主动互动（如战绩截图→夸打得好）；游戏编辑部在数十款游戏数千场景中定制触发 | 【推测】混合式：语义检索（相似场景召回）+ 规则/标签触发（游戏状态机、编辑场景）。官方未披露向量库/图结构等细节 |
| **跨场景泛化** | 支持 110+ 游戏通用视觉识别 + 生活场景（看剧/网购/学习/编程/工作）；用户提供的案例：哈迪斯2讨厌锤子→下次玩空洞骑士会调侃【用户提供，未独立核实】 | 【推测】泛化能力来自"存语义不存应用"：VLM 把画面转成语义理解，记忆绑定"行为/情绪语义"而非某个游戏 ID，故偏好可跨场景迁移 |

**关键洞察**：逗逗的记忆抽象级别是 **"语义场景"**——它把"当时在干什么、什么情绪、聊了什么"打包成一个可回忆、可迁移、可回放的单元，而不是"某游戏的某段录像"或"某句话"。这正是跨场景联想（锤子梗）成立的原因。官方文章也明确：感知（VLM 看画面）是这一切的上游，记忆是对感知产物的再组织。

## 2. 两级抽象差距

| 维度 | 逗逗 · 场景级记忆 | oc-pet · 事件级文本记忆（已核实代码） |
|------|------------------|--------------------------------------|
| **存储单元** | 多模态融合的"场景"（画面+声音+对话+情绪，一个语义单元） | 单条文本/统计：`today` 分类计数、`last_topic`（≤60 字字符串）、`history` 7 天每日摘要（`core/companion_memory.py`） |
| **感知来源** | 实时 VLM 看画面 + RTC 语音听情绪（云端大模型，常开） | 前台窗口分类 + 时间/活动信号 + **可选**视觉 API 的 `ActivityEvent`（`core/perception/screen.py`，含 summary/detail/start/end，**未写入记忆**） |
| **检索方式** | 未公开；推测语义检索 + 场景标签/规则触发 | 无检索：只取"最近一条"`last_topic` 或"昨日"摘要（线性时间，`yesterday_summary()`） |
| **回忆表现** | 跨场景联想、高光回放、关系进化、"千人千面" | 机械接话："你昨天说的「X」后来怎么样了？"（`core/companion_hooks.py`）；超过 7 天无痕迹；昨日之外基本想不起来 |
| **技术成本** | 高：VLM 常开 + RTC + 长上下文 + 云端存储/算力 | 极低：JSON/文本，KB 级，纯本地，无新依赖 |
| **隐私/依赖** | 云端处理画面/声音（官方声明 VLM 范围限游戏/浏览器） | 全本地、可离线；视觉 API 为可选（用户配置 key 才启用） |

**一句话差距**：逗逗赢在"把感知直接编码成可跨场景检索的记忆"；oc-pet 目前是"感知→反应"直连（`scenarios.py` 只做文案触发器），"感知→记忆"断链。

## 3. "更底层"意味着什么

### 3.1 判断"对"在哪

1. **感知层确实更基础**：oc-pet 的前台分类/意图（5 意图 + 10 场景）/情绪/活动信号，是任何记忆系统（无论文本还是场景）的上游。方向上同源——`scenarios.py` 已有"场景"概念雏形，只是它目前是反应文案的 key，还不是记忆单元。
2. **文本事件是场景记忆的天然原材料**：`screen_types.ActivityEvent` 已含 `app / activity / category / summary / detail / start_time / end_time`——数据模型上离"场景"只差一层组织。`last_topic`（≤60 字）就是"对话模态"的轻量投影。
3. **纯本地/轻量约束倒逼"文本投影"路线**：不依赖 VLM 常开，长期更可持续、更隐私，且随时可升级。

### 3.2 判断"错/需修正"在哪

- **"更底层" ≠ "更接近终局"**。逗逗的护城河不在感知（感知能力大厂都能堆），而在 **感知→场景→关系→自我认知→反哺行为** 的闭环。oc-pet 的感知层产出目前**没有沉淀进记忆**：`ActivityEvent` 的 summary/detail 被丢弃，`CompanionMemory` 只存计数与最后一条话题。底层信号再多，不变成"可回忆的结构"，就仍只是"实时反应器"，而非"有记忆的伙伴"。
- 用户问的"缺哪一层"——准确答案是**缺三层**（多模态编码其实不是必需的）：

| 缺失层 | 说明 | oc-pet 现状 |
|--------|------|-------------|
| ① 事件流采集层 | 把感知信号（分类/场景/情绪/话题）持续写入带时间轴的流 | ❌ 只有 `today` 计数 + `last_topic` 单点，无持续事件流 |
| ② 场景聚类层 | 把零散事件聚成可回忆的语义单元（同主题/同游戏/同情绪的连续片段） | ❌ 无；`history` 只有日级摘要，无场景粒度 |
| ③ 回忆触发层 | 当前感知状态命中历史场景 → 主动回忆/跨场景联想 | ⚠️ 半缺：只有"跨天首启"一个触发点（`build_morning_greeting`），无场景级触发、无联想 |

### 3.3 结论

oc-pet 的文本事件数据**天然是场景记忆的原材料**，不是另起炉灶；"更底层"要变成优势，必须补上"从信号到记忆"的抽象层。低成本路径 = **不做多模态编码，做"文本投影 + 轻量聚类 + 规则触发"**，在纯本地/JSON 约束内逼近"场景记忆"的最小可用形态。

## 4. 低成本借鉴建议（按优先级排序）

> 约束复核：纯本地、无 VLM 常开、JSON/文本级、模块极简（0x8001010D 未根除，任何新增必须可独立回滚、不碰主渲染线程）。

### 建议 A【P0】把 `today` 分类升级为带时间轴的事件流

- **做什么**：新增轻量事件流文件（`~/.oc-pet/memory/<agent_id>_events.jsonl`，逐行 JSON，append 写入，损坏不影响主记忆 JSON）。事件字段：`{ts, start_ts, end_ts, category, scenario, intent, emotion, topic?}`。改造 `record_activity` / `record_topic` / 感知层 hook 落盘事件流，**保留**现有 `today`/`history`/`streak` 统计与 `yesterday_summary()` 接口（向后兼容，P2 验收"你昨天说的那个项目"不受影响）。
- **改动量预估**：新文件 + `CompanionMemory` 扩展 2-3 个方法 + `controller.py`/`screen.py` 接线，约 100–150 行，无新依赖。
- **验收标准**：连续使用 3 天可导出按时间排序的事件流；事件含时间/分类/情绪字段；旧记忆 JSON 兼容不丢；单条 append 写入，崩溃不损坏既有行。

### 建议 B【P1】为事件加"情绪标签"

- **做什么**：把 `EmotionStateMachine` 的当前情绪（emotion + intensity）在事件结束时快照进事件流；`last_topic` 记录时附带情绪。让"深夜加班（焦虑）" vs "深夜打游戏（开心）"可区分——这是场景语义最关键的一维。
- **改动量预估**：记录接口加参数 + emotion 读取点接线，约 30–50 行。
- **验收标准**：事件流 ≥90% 条目带情绪标签；次日问候可按情绪选文案（昨日焦虑→更温柔）；情绪读取为纯内存快照，不新增崩溃点。

### 建议 C【P1】轻量"场景聚类"：事件流 → 场景表

- **做什么**：新增 `core/perception/scene_cluster.py`（纯函数，无新依赖）。规则聚类：同一 `category/scenario` + 时间窗（如连续 ≥20 分钟）→ 生成场景 `{scene_id, label, tags, first_ts, last_ts, count, emotion_summary, topics[]}`；"深夜加班/打某游戏/追剧"各自成为一条场景，重复场景计数（第 N 次深夜加班）。每日收盘跑一次，结果存 `~/.oc-pet/memory/<agent_id>_scenes.json`。
- **改动量预估**：新增 1 个模块约 150–200 行 + 收盘调用点。
- **验收标准**：7 天数据能聚出 ≥5 条可读场景；场景标签可被问候/回忆文案引用；聚类耗时 <1s；文件 ≤ 几百 KB。

### 建议 D【P1】按场景触发回忆台词（轻量"回放"）

- **做什么**：复用 `scenarios.py` 文案池机制，新增"回忆型文案"：当前感知状态命中某历史场景标签时（如又在打同一游戏、又是深夜加班），主动说一句带记忆的话（用场景里的 topic/tags 拼接，如"上次你打到那关卡了很久，这次应该过了吧？"）；带冷却（30min+）并沿用 `is_disruptive` 打扰判定（打字中不打扰）。
- **改动量预估**：场景表读取 + `proactive.py` 增加一个 hook + 文案模板，约 80–120 行。
- **验收标准**：同一场景第二次出现能触发 ≥1 条带记忆台词；冷却生效；与现有主动对话经事件总线不冲突。

### 建议 E【P2】跨场景联想（简单规则版）

- **做什么**：不做向量，用"情绪标签/主题标签"交集做跨场景关联：如"上次深夜加班后你聊过 X"→ 下次深夜加班时提一句；游戏偏好→看剧推荐（同标签）。带开关可关。
- **改动量预估**：联想函数 + 模板，约 50–80 行。
- **验收标准**：产出 ≥1 个真实可用的跨场景联想案例；误触发率低（可配置关闭）。

**路径说明**：A（事件流地基）→ B（情绪维度，便宜）→ C（场景形成）→ D（把场景变成用户可感知的"回忆"）→ E（进阶联想）。每步独立、可回滚、可单独验收，不阻塞现有 P1/P2 排期。

## 6. deepseek-hanako 桌宠架构借鉴分析

### 6.1 架构要点（已核实仓库 README）

| 维度 | deepseek-hanako（鲸鱼娘·溟月） |

### 6.2 借鉴点评估（对应任务 a/b/c）

#### a. "HTTP 状态机解耦"模式对 oc-pet 的价值

**现状核实**：oc-pet 情绪/动画在进程内——`EventBus`（进程级 pub/sub）、`conversation_engine.on_reply` 回调带 emotion/anim/audio_path、`EmotionStateMachine`、`scenarios.py`→emotion/anim。已有跨模块桥全部为进程内：`multi_pet_bridge`（多宠）、`pet_audio_bridge`（音频事件）、`capability_registry`（指令快路径）、`hanako_monitor`（生命周期→情绪）。**外部程序无法读取/驱动桌宠状态。**

**关键先例**：`core/phone_receiver.py` 已是 stdlib `HTTPServer` 绑 `127.0.0.1:8077` 的后台线程范式（收 MacroDroid 手机事件，带 `X-Auth-Token`、JSON 响应、日志抑制）。**"本地 HTTP 口"在 oc-pet 代码库已有成熟范式，F 建议是复用该范式，不是新造轮子。**

**评估**：
- 价值真实：一个极简本地状态口（哪怕只读）能让**任意外部程序**（构建脚本、游戏、自动化工具、另一只桌宠、智能家居桥）查询/驱动桌宠，把 oc-pet 变成"可被其他软件对话的数字伙伴"。deepseek-hanako 证明成本极低（Electron 内几百行）。
- 约束适配：stdlib 即可（无新依赖）；只绑 127.0.0.1；守护线程；**默认关闭**（config 开关）；只读 `GET /state` 先行，写仅允许白名单词汇并经 `EventBus.emit` 走现有处理链（不直接碰 Live2D 渲染线程）；独立文件、可整体回滚。
- 结论：**值得，P2，严格护栏**。

#### b. hana-bridge 事件桥接 vs oc-pet 已有机制

**现状核实（关键发现）**：oc-pet **已有等价物**——`hanako_monitor.py` 的 `EVENT_TO_MOOD`（thinking_start→thinking、vision_progress/tool_start→working、tool_end→idle 且 success→happy/error）经 WebSocket 事件实时映射情绪，比 hana-bridge 更早同构。`capability_registry` 是"用户指令→动作"快路径，`companion_hooks` 是生命周期钩子，`pet_audio_bridge` 是音频事件桥。

**差异**：deepseek-hanako 把生命周期映射为**干净的 6 态动画状态机并外置**（HTTP 可查）；oc-pet 映射为**情绪/mood 标签**，且缺"完成→庆祝"语义（`config.py` 中 happy→waving，无 celebrating）。

**结论**：**不需要照搬 hana-bridge**；可借鉴的是**补全"桌宠状态词表"（对齐 6 态含 celebrating）+ 完成态庆祝**（见建议 G）。

#### c. 轻量动画（程序 transform + 少帧精灵图）对 oc-pet 的意义

**现状核实**：oc-pet 是 Live2D + PySide6（形态不同）；**idle 微动作已存在且更丰富**——`pet_mixins/behavior_mixin.py` 有 `_idle_action_cd`（8-20s / 10-24s 随机）、低优先级 motion（比心/挥手/唱歌/思考）、`_idle_face_cd` 表情微动作；动画词表已接近（`conversation_engine.py` anim：wave/happy/thinking/working/sleep/surprised 等）。

**结论**：**直接借鉴价值低**（CSS transform 不适合 Live2D）。唯一可选借鉴点是"待机低开销"——idle 时避免高频 Live2D motion 调用，用渲染层轻量叠加（呼吸/漂浮）降 CPU/GPU，但需开发评估 Live2D idle 是否已足够轻；若已够则仅作验证、不动作。列为 P2 可选优化。

## 7. oc-pet 升级全景图（记忆层 A-E + 表现/联动层 F-G）

> 合并说明：A-E 沿用第 4 章结论（**不推翻**）；F/G 为新增的表现/联动层建议。全部纯本地 / JSON 级 / 无新依赖 / 可独立回滚。

### 7.1 全景总表

| 编号 | 层 | 建议 | 优先级 | 改动量（预估） | 验收标准 |
|------|----|------|:---:|------|----------|
| A | 记忆 | `today` 升级为带时间轴的事件流 | P0 | ~100-150 行，无新依赖 | 连续 3 天可导出按时间排序事件流；含时间/分类/情绪字段；旧 JSON 兼容；append 崩溃不损坏 |
| B | 记忆 | 事件加"情绪标签" | P1 | ~30-50 行 | 事件流 ≥90% 条目带情绪；次日问候可按情绪选文案 |
| C | 记忆 | 轻量场景聚类（事件流→场景表） | P1 | 新模块 ~150-200 行 | 7 天聚出 ≥5 条可读场景；聚类 <1s；文件 ≤几百 KB |
| D | 记忆 | 按场景触发回忆台词（轻量"回放"） | P1 | ~80-120 行 | 同场景二次出现触发带记忆台词；冷却 30min+；不打扰场景沿用 `is_disruptive` |
| E | 记忆 | 跨场景联想（简单规则版） | P2 | ~50-80 行 | ≥1 个真实联想案例；可开关 |
| G | 表现/联动 | 补全桌宠状态词表（对齐 6 态含 celebrating）+ 完成态庆祝 | P1 | ~50-100 行 + 素材复用 | hanako `tool_end` 成功 → celebrating（撒花动作 + 可选完工音）；词表可被 F 只读口输出 |
| F | 表现/联动 | 极简本地状态口（HTTP 只读 `GET /pet/state`，可选写） | P2 | 复用 `phone_receiver.py` 范式 ~100-150 行 | 默认关闭；127.0.0.1；GET 返回 emotion/scenario/status；写白名单校验；可回滚 |

**排序说明**：记忆层 A→B→C→D→E 为地基到体验的渐进路径（沿用上一版）；表现层 G 先行（P1 独立小步、为 F 提供词表），F 后置（P2，依赖 G 的词表 + `phone_receiver.py` 范式）。

### 7.2 落地顺序建议

- **第一梯队（P0-P1 记忆地基）**：A → B → C → D
- **第二梯队（P1 表现小步）**：G（独立、不依赖记忆层）
- **第三梯队（P2 联动/优化）**：E、F、（可选）待机低开销评估
